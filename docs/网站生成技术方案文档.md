# 网站生成技术方案文档

## 1. 文档目的与范围

本文档基于当前代码实现，说明 `builder` 内“企业网站一键生成”链路的技术设计、关键约束、质量门禁、可观测性和扩展方案。

覆盖范围：
- API 入口与持久化
- Architect/Builder 双阶段生成图
- 模板解析与多策略候选
- 页面/路由/链接契约
- 结构化输入与检索增强（Serper）
- QA Gate 与 Payload Audit
- Sandbox 预览与可编辑能力

核心代码入口：
- `builder/src/app/api/creation/route.ts`
- `builder/src/lib/agent/p2w-graph.ts`
- `builder/src/lib/agent/contracts.ts`
- `builder/src/lib/agent/qa-gate.ts`
- `builder/src/lib/agent/template-resolver.ts`
- `builder/src/lib/agent/section-template-registry.ts`
- `builder/src/lib/agent/link-graph.ts`
- `builder/src/lib/site-payload-audit.ts`

## 2. 目标与非目标

### 2.1 目标

1. 一次请求生成多页面企业官网（默认含 home/about/contact/privacy 及至少一个业务页）。
2. 支持自然语言 + 结构化输入（JSON/CSV）混合驱动。
3. 自动统一站点主题、导航、页脚与站内链接。
4. 在生成后执行硬门禁（contract + QA + payload audit），阻断高风险结果。
5. 输出可在 sandbox 预览并可被 Puck 编辑的数据结构。

### 2.2 非目标

1. 不追求像素级还原任意外部网站（该能力在 template-factory fidelity 链路）。
2. 不在运行时依赖前端 JIT 代码编译作为唯一渲染路径（生产偏向静态可注册 block）。

## 3. 端到端架构

```mermaid
flowchart TD
  A[POST /api/creation] --> B[parseStructuredSiteInput]
  B --> C[generateP2WProject]
  C --> D[Serper Fact Pack]
  D --> E[StateGraph: Architect]
  E --> F[StateGraph: Builder]
  F --> G[Contract Validation]
  G --> H[QA Gate]
  H --> I[Payload Audit]
  I --> J[Persist result.json + sandbox/payload.json + audit.json]
  J --> K[/creation/sandbox 预览 + Puck 编辑]
```

### 3.1 API 层（`route.ts`）

- 入口：`POST /api/creation`
- 关键能力：
  - 解析 `prompt`
  - 解析结构化输入：`parseStructuredSiteInput`
  - 调用核心生成：`generateP2WProject`
  - 超时处理：请求级 timeout + deferred persist watchdog
  - 审计：`auditSitePayload`
  - 持久化：`result.json`、`sandbox/payload.json`、`audit.json`

### 3.2 Agent 图（`p2w-graph.ts`）

- 图结构：`START -> architect -> builder -> END`
- Architect：输出站点蓝图（theme + pages + sections）
- Builder：完成模板匹配、section 生成、全站统一化、门禁评估

### 3.3 渲染与编辑层（Sandbox）

- 页面入口：`builder/src/app/creation/sandbox/page.tsx`
- 客户端：`builder/src/app/creation/sandbox-client.tsx`
- 能力：
  - 读取 payload
  - route canonical + sandbox page 参数重写
  - 主题变量注入（Tailwind runtime config）
  - 支持 skinnable slots（text/image/link/style）

## 4. 数据模型与契约

### 4.1 输入契约

#### 自然语言输入
- `prompt` 为主，支持中英混合。

#### 结构化输入（优先）
- 由 `StructuredSiteInput` 表示：
  - `company`
  - `nav/pages`
  - `products/cases/faqs`
  - `contactFields`
  - `targetLanguage`
  - `catalogPageSize`

说明：结构化输入被拼接为 `structuredPromptPatch`，并参与后续页面补齐、内容生成与 QA 评估。

### 4.2 路由契约（Route Contract）

- 统一 canonical route（`route-contract.ts`）
- 典型映射：
  - `/home` -> `/`
  - `/product` -> `/products`
  - `/custom-solutions` -> `/solutions`
  - `/applications` -> `/cases`
  - `/privacy-policy` -> `/privacy`

### 4.3 站点契约（Site Contract）

`contracts.ts` 提供两阶段能力：
1. `normalizePagesBySiteContract`
2. `validateGeneratedSiteContract`

硬约束包含：
- 必须有首页 `/`
- 企业站必须满足 required page types（含 `/privacy`）
- contact 页必须有 lead capture
- contact 页禁止渐变文本（`text-gradient/bg-clip-text/text-transparent`）
- 语言一致性检查（中文请求 vs 英文落地）
- 模板占位文案检测（lorem ipsum/your brand/{{...}} 等）

## 5. 生成主流程（详细）

## 5.1 请求进入

1. `route.ts` 解析 prompt/structured input。
2. 检查 LLM provider 可用性（Aiberm/OpenRouter/Anthropic）。
3. 根据 strict contract 与 persist 模式选择 timeout。
4. 调用 `generateP2WProject`。

## 5.2 检索增强（Serper）

- `buildSerperFactPack(prompt, structuredInput)`
- 固定 required fields：`company/products/specs/cases/faq`
- 若字段缺失，按预算发 query；将结果作为 `External Fact Pack` 拼入 prompt。

价值：
- 降低“信息密度不足”导致的页面空洞。
- 缩短用户补充资料的交互轮次。

## 5.3 Architect 阶段

1. 优先尝试 template/enterprise seed blueprint。
2. 否则调用 LLM 工具化输出 blueprint。
3. 空结果/弱结果时走 retry + compact + fallback blueprint。
4. 应用：
  - 用户主题意图
  - 引用约束
  - prompt 请求页面补齐
  - 企业站页面补齐
  - site contract normalize

输出：`blueprint`

## 5.4 Builder 阶段

1. 合并 requested pages + structured brief。
2. 企业站补 `/privacy`，必要时补全标准页面。
3. pre-template 合同归一化。
4. `orchestrateTemplateAndSectionCandidates`：
  - page-type hardness 注入
  - section 顺序重排
  - 重复 section 去重预算
  - 策略建议（template_first/hybrid/llm_first）
5. `resolveTemplatePlan`：按 full-site/page/section/block/llm 分层选解。
6. post-template 合同归一化。
7. 构建 `siteBlueprint` + `linkGraph`。
8. 逐 section 生成（失败可 deterministic fallback block）。
9. 统一 navbar/footer，清洗 href。
10. 运行 contract gate + QA gate。

输出：`pages/components/theme/siteBlueprint/qaReport/resolvedByLayer/errors`

## 5.5 多候选策略选择

- `resolveCandidateStrategiesForPrompt` 计算策略候选集合。
- 每个候选运行 graph，`scoreGenerationCandidate` 打分。
- 评分维度：pass、overall/semantic/coverage/link/theme、layer、fallback/error penalties。
- 选最优候选，附带 `candidateSelection` 诊断。

## 6. 模板与内容协同机制

### 6.1 模板选择

- 数据源：`style-profiles.generated.json`（可由 template-factory 发布）
- 选择器：`selectStyleProfile`
- 解析器：`template-resolver.ts`
  - pageType 推断
  - path-specific default kinds
  - prompt-driven kinds
  - mandatory global chrome kinds

### 6.2 Hardness 机制

- 规则定义：`page-rule-matrix.ts`
- 作用点：`skill-orchestrator.ts`
- 能力：
  - 不同页面类型的 nav/hero/content 节奏与结构约束
  - section 重复预算
  - 关键页面对（`/core-product` vs `/products`，`/solutions` vs `/cases`）防同构

### 6.3 链接与全局壳层一致性

- `link-graph.ts` 负责：
  - nav/footer 标准结构
  - href canonical 化
  - 非信任外链回退
  - 内链缺失 fallback 到 home

## 7. 质量门禁体系

## 7.1 Site Contract Gate

- 关注“是否符合企业站最小可用合同”
- 错误级别阻断 `pass`

## 7.2 QA Gate（`qa-gate.ts`）

评分项：
- `coverageScore`
- `linkIntegrityScore`
- `themeConsistencyScore`
- `middleSectionScore`
- `semanticFidelityScore`
- `overallScore`

典型问题项：
- missing pages
- broken links
- theme inconsistency
- language mismatch
- template copy
- repetitive structure pairs
- critical duplicate pairs

## 7.3 Payload Audit（`site-payload-audit.ts`）

关注发布前结构安全：
- unknown block type
- fallback block 残留
- duplicate page path
- high template reuse / structural similarity
- template adaptation mismatch
- contact gradient 违禁

当 `audit.ok=false` 时，`publishStatus=blocked`。

## 8. Provider 与容错

### 8.1 Provider 顺序

`builder/src/lib/agent/graph.ts`：
- 默认顺序：`aiberm -> openrouter -> anthropic`
- 支持环境变量覆盖：`LLM_PROVIDER_ORDER` / `LLM_PROVIDER`
- 当 primary 为 aiberm 且 openrouter key 可用时，可自动注入 openrouter fallback

### 8.2 LLM 调用层容错

`p2w-graph.ts`：
- 支持 local timeout
- provider fallback（按错误类型和开关）
- fallback model
- section 级 deterministic fallback block

### 8.3 请求级容错

`route.ts`：
- 超时返回 pending/fallback
- 异步持久化结果
- watchdog 超时后落盘 timeout fallback

## 11. 与 Puck Editor 的兼容设计

1. 输出 payload 保持 `components + pages + theme` 结构。
2. 页面内容为 block 列表，支持 Puck 渲染与编辑。
3. `sandbox-client` 提供 skinnable slot 编辑导出能力。
4. 链接 canonical 化与 page 参数重写在 sandbox 内完成，不破坏编辑数据结构。

结论：站点生成链路调整时，必须同步验证 Puck 可编辑性；当前实现已把编辑适配作为运行时第一等能力处理。

## 12. 扩展指南

### 12.1 新增页面类型

1. 扩展 `page-classifier.ts` 与 `page-rule-matrix.ts`
2. 更新 `template-resolver.ts` defaultKinds/pathSpecificKinds
3. 更新 `enterprise-site-structure.json`（如需纳入企业站必备页）
4. 增加 contract/qa 对应规则

### 12.2 新增 section 模板

1. 在模板库写入 block 与 generation contract
2. `section-template-registry.ts` 可自动读取发布资产
3. 通过 `orchestrateTemplateAndSectionCandidates` 赋予页面类型权重

### 12.3 新增 skill 编排

建议以“增量 skill”方式并行编排，不直接改已有 skill：
- 页面类型 skill（home/products/solutions/cases/about/contact/privacy）
- 全局 skill（theme/nav-footer/link normalization/qa repair）

---

## 13. 商用验收标准（建议）

1. Contract Gate：0 error。
2. QA Gate：overall >= 阈值，且无 criticalDuplicatePairs。
3. Payload Audit：`ok=true`，unknown/fallback block 为 0。
4. 全站导航与页脚在所有页面一致，内链均为 sandbox 可达路由。
5. 请求语言与落地文案语言一致（中文输入不出现英文模板残留）。
6. Contact 页存在有效线索采集能力，且禁用渐变文字。

---

## 14. 已知风险与治理建议

1. 风险：模板残留文案在 fallback 情况下泄漏。
- 治理：把“模板占位词检测”维持为 contract error，并在 builder 后处理阶段做二次替换。

2. 风险：检索增强未覆盖时内容密度不足。
- 治理：对 required fields 做配额化必跑，未覆盖字段进入生成提示硬约束。

3. 风险：页面同构（结构相似度过高）。
- 治理：保留 page-type hardness + 关键页面对去同构 patch + qa/payload similarity gate。

4. 风险：外链污染导航。
- 治理：`link-graph.ts` 持续限制 trusted hosts，其他绝对链接回退内链。

---

## 15. 总结

当前网站生成方案已具备“输入标准化 -> 双阶段生成 -> 契约/质量门禁 -> 可编辑预览”的完整闭环。后续优化重点应放在：
- 强化结构化输入优先级
- 提升检索覆盖与内容扩写质量
- 继续降低页面同构率
- 通过模板工厂持续补充高质量 page/section 模板资产
